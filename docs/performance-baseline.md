# 大题库侧栏性能基线

## 运行

使用 Node.js 24，从仓库根目录运行：

```bash
npm run build
npx tsx scripts/benchmark-sidebar.ts > .tmp/sidebar-benchmark.json
```

脚本使用生产构建的 Electron 界面，对 1,000 和 5,000 道题各测三轮。不与构建、测试或截图生成并行运行，也不使用真实题库。每轮创建独立的应用数据与合成工作区；退出 Electron 进程后清理。本次测量不会改变用户工作区或正式应用的最近记录。

合成数据固定为十章，题目含三段 LaTeX 和两个短标签，10% 的题目含“基准命中”标签。窗口为 1470×891，不做 CPU 降速。该数据代表普通短题目，不代表大量图片、超长公式或大型掌握历史的题库。

## 指标解释

- `loadMs`：已有 Electron 进程内重新加载生产页面，到逻辑题数正确、首个可见题目行和编辑器可用并经过两个绘制帧。不是冷启动耗时。
- `dom`：加载后的全页／侧栏 DOM 元素数量和加载阶段超过 50ms 的主线程任务。
- `filter`／`clearSearch`：筛选到 10% 题目／清空筛选恢复全量题目。
- `switchItem`：切换到第二题并确认原编号更新。
- `scroll`：用 60 个动画帧把侧栏滚到底，记录最长帧间隔。不是原生滚轮或触控板输入测试，总时长至少约一秒。
- `editAndSave`：输入短文本并等待题库保存成功，包含自动保存的 500ms 防抖。
- `saveHttpMs`：该次保存请求发送到响应完成，包含传输和服务端处理，不能等同于纯磁盘写入耗时。

交互耗时包括 Playwright 操作、状态断言与两个绘制帧，适合在同机同环境下比较，不作为精确的用户输入延迟。长任务指标仅描述主线程，不能单独归因于 React、MathJax 或浏览器布局。基准没有固定性能门禁；失败的断言或超时会使命令失败，不能把不完整结果当作通过。

桌面虚拟列表必须保持章节吸顶、变高题目行、导出勾选、拖拽排序和键盘焦点行为。760px 以下保留普通列表；本基准不代表窄屏性能。

## 2026-09-12：桌面侧栏动态高度虚拟化

环境：Apple M4／16 GiB／Node 24.20.0，1470×891，生产 Electron，各题数三轮，无并行构建、测试或截图任务。修改前使用提交 `821de28` 的隔离源码快照；前后使用同一份调整后的基准脚本和依赖安装。虚拟化后不能再以“全部题目均存在于 DOM”作为加载／筛选完成条件，因此本轮统一校验逻辑题数、可见题目和两个绘制帧，并通过精确选择器定位搜索和计数控件，避免全页无障碍名称扫描放大旧版耗时。不要把本表与上一次不同断言方法的数字直接作提速比较。

以下为三轮中位数，耗时单位 ms：

| 指标 | 1,000 题修改前 | 1,000 题修改后 | 5,000 题修改前 | 5,000 题修改后 |
| --- | ---: | ---: | ---: | ---: |
| 页面重新加载 | 433 | 507 | 4,350 | 504 |
| 筛选到 10% | 81 | 49 | 357 | 49 |
| 清空筛选 | 148 | 65 | 5,215 | 65 |
| 切题 | 83 | 75 | 149 | 67 |
| 输入并保存（含防抖） | 819 | 729 | 1,214 | 830 |
| 侧栏 DOM 元素数 | 24,020 | 321 | 120,020 | 321 |

5,000 题清空筛选降低约 98.8%，侧栏初始 DOM 降低约 99.7%，达到本轮“清空筛选 ≤1 秒且降低至少 70%、DOM 降低至少 90%”的验收目标。1,000 题重新加载增加 74ms（约 17%）；此处保留结果，不声称所有场景均提速，也没有足够样本把差异归因于某个组件。这些时间仍包括自动化操作、断言及绘制等待，不等同于纯 React 执行时间。

题目行使用 TanStack Virtual 动态测高；章节标题保留原生 sticky 与章节交接。只挂载可见题目、缓冲行、焦点附近和拖拽来源行；章节容器及标题保留以界定吸顶范围。因此 DOM 仍随章节数量增长，本次十章数据不能证明极端多章节题库的性能。完整选择、筛选和排序使用原数据模型。桌面回归覆盖长标签、窄侧栏、跨挂载边界的 Tab/Shift+Tab、滚动后焦点保留、拖拽、已选列表及窄屏切换。

## 2026-09-11：修正切题测量范围

本次 CPU profile 显示，旧基准在 5,000 题切题步骤中约 2,627ms 花在 Playwright 注入脚本的 `getElementLabels`，即全页 `getByLabel("原编号")` 扫描；不能将旧表中约 2.8 秒归因为应用切题。基准现在将该断言限定在 `#main-workspace` 内，保留真实点击、值校验和两个绘制帧。

在 Apple M4／16 GiB／Node 24.20.0、生产 Electron、无并行构建或测试的条件下重新运行三轮，中位数如下：

| 指标 | 1,000 题 | 5,000 题 |
| --- | ---: | ---: |
| 页面重新加载 | 673ms | 4,400ms |
| 筛选到 10% | 82ms | 384ms |
| 清空筛选 | 365ms | 6,468ms |
| 切题（限定断言范围） | 82ms | 124ms |
| 输入并保存（含防抖） | 783ms | 1,318ms |

这里的切题数字是测量方法纠正，**不是产品优化带来的提速**。代码复核确认侧栏行已使用 `memo`、稳定回调和缓存后的查找表，本轮没有再叠加缓存或引入虚拟列表。旧“切题降低 30%”目标不能作为优化验收依据。清空筛选仍有明显耗时，全量挂载仍约 12 万 DOM；后续应针对列表恢复单独剖析，并在保持章节吸顶、拖拽与键盘焦点的约束下设计减少挂载行数的方案。

## 2026-09-10 测量结果（旧方法，切题指标已被上文纠正）

环境：macOS arm64，Apple M4，16 GiB 内存，Node 24.20.0，Electron 42.11.1；生产构建，无并行构建／测试。以下为三轮中位数，单位 ms。

| 指标 | 1,000 题 | 5,000 题 |
| --- | ---: | ---: |
| 页面重新加载 | 649 | 4,319 |
| 筛选到 10% 题目 | 81 | 380 |
| 清空筛选恢复全量 | 365 | 6,732 |
| 切换题目 | 184 | 2,802 |
| 输入短文本并完成保存（含防抖） | 796 | 1,233 |
| 保存 HTTP 请求 | 65 | 136 |
| 侧栏 DOM 元素数 | 24,020 | 120,020 |
| 全页 DOM 元素数 | 24,427 | 120,427 |

原始三轮耗时：

| 题数 | 加载 | 筛选 | 清空筛选 | 切题 | 输入并保存 | 保存 HTTP |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 649 / 856 / 644 | 81 / 81 / 83 | 365 / 365 / 361 | 199 / 184 / 182 | 1,012 / 796 / 762 | 63 / 69 / 65 |
| 5,000 | 4,319 / 4,305 / 4,320 | 380 / 393 / 349 | 6,732 / 6,739 / 6,678 | 2,741 / 2,816 / 2,802 | 1,233 / 1,234 / 1,213 | 126 / 136 / 137 |

五千题清空筛选的最长主线程任务分别为 1,282 / 1,305 / 1,273ms；切题为 2,609 / 2,659 / 2,652ms。千题滚动的最大帧间隔为 18 / 19 / 18ms，五千题为 18 / 18 / 22ms。滚动总测量时间分别约 1.15s 与 3.66s，包含操作开始前后的自动化通信和绘制等待，不能据此直接声称持续掉帧。

合成题库 JSON 大小分别为 498,356 和 2,503,556 字节。本次五千题清空筛选超过了 Playwright 默认 5 秒断言期限；基准使用 30 秒期限完成全部六轮采样，这只是测量上限，并非产品性能目标。

据这些结果推断，下一步应优先对侧栏全量恢复及切题时的主线程工作做性能剖析，并评估减少挂载行数。暂不优先调整保存协议：本次 HTTP 保存耗时远低于恢复列表和切题耗时。当前数据不能区分其中 React 协调、浏览器样式布局和 MathJax 各自占比，也不覆盖原生拖动／触控板体验。后续实现需另行确认。
